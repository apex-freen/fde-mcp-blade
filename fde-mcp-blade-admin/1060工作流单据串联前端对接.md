| # | 位置 | 性质 | 内容 |
|---|---|---|---|
| **①** | 管理后台 →「**工作流管理**」 | **全新页面**（配置类，放 controller） | **拖拽式**编辑（把插件能力拖成节点）+ 下拉式可见域；列表 / 新建 / 编辑 / 发布 / 停用 / 删除 / 导入 / 导出 / 变更历史 |

## 二、通用约定

| 项 | 约定 |
|---|---|
| **Base** | 所有接口挂在 `/prod-api` 之下，例：`/prod-api/biz/gis_workflow` |
| **鉴权** | `Authorization: Bearer <登录 token>`（就是现有的登录态，无需额外令牌） |
| **响应包装** | 统一 `{ "code": 200, "msg": "操作成功", "data": ... }`；失败 `code` 非 200、`msg` 为中文可直显文案 |
| **分页返回** | 统一 `{ "total": <总数>, "rows": [...] }` |
| **时间格式** | 出参统一字符串 `YYYY-MM-DD HH:MM:SS`（**不要**自己从时间戳转） |
| **布尔/可空** | 可空字段直接返回 `null`，请按空值渲染（不要显示 "null"） |
| **路由风格** | **RESTful**：集合 `GET/POST /biz/gis_workflow`、单资源 `GET/PUT/DELETE /biz/gis_workflow/{code}` |
| **注意** | `import` 是**静态路径**，注册在 `{code}` 之前；前端拼接 URL 时不要把它当编码 |

## 三、接口契约 A：工作流管理

> 路由前缀：`/prod-api/biz/gis_workflow`

### A1. 列表

```
GET /biz/gis_workflow?keyword=&status=&page=1&page_size=10
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `keyword` | string | 否 | 编码 / 名称模糊匹配 |
| `status` | string | 否 | 生命周期过滤：`draft` / `published` / `disabled`；不传 = 全部 |
| `page` / `page_size` | int | 否 | 默认 1 / 10 |

```json
{
  "code": 200,
  "data": {
    "total": 1,
    "rows": [
      {
        "code": "dish",
        "name": "做菜",
        "description": "从买菜到上桌的完整流程",
        "status": "published",
        "prefix": "dish",
        "enforce_mode": "shadow",
        "scope": "org",
        "scope_ref": null,
        "current_version": 2,
        "stage_count": 3,
        "can_manage": true
      }
    ]
  }
}
```

- `can_manage`：**服务端已判定"当前用户能否管理这条工作流"**，前端**直接用它**控制按钮显隐，**不要按 `scope` 自己猜**。
- **列表已按可见域过滤**：不同用户看到的条数不同，这是预期行为（`org` 全员可见 / `dept` 仅本部门 / `user` 仅本人 / 管理员全见）。

### A2. 新建

```
POST /biz/gis_workflow
```

```json
{
  "code": "dish",
  "name": "做菜",
  "description": "从买菜到上桌的完整流程",
  "prefix": "dish",
  "enforce_mode": "shadow",
  "scope": "org",
  "scope_ref": null,
  "stages": [
    { "stage": "buy",  "seq": 1, "name": "买菜", "manual_minutes": 25, "methods": ["kitchen.buy"] },
    { "stage": "wash", "seq": 2, "name": "洗菜", "manual_minutes": 10, "methods": ["kitchen.wash"] },
    { "stage": "cook", "seq": 3, "name": "烧菜", "manual_minutes": 30, "methods": ["kitchen.cook"] }
  ]
}
```

字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `code` | ✅ | 工作流编码（**主键，创建后不可改**）；建议英文小写+短横线/下划线 |
| `name` | ✅ | 中文名称（无 `prefix` 时前缀回落为 `code`，所以 `code` 要有可读性） |
| `description` | 否 | 说明；会出现在 `workflow_get` 给智能体的输出里 |
| `prefix` | 否 | **单号前缀**；不传 = 用 `code`。单号形如 `{prefix}-{yyyyMMdd}-{6位随机}` |
| `enforce_mode` | 否 | `shadow`（默认，只记不拦）/ `enforce`（强制拦截） |
| `scope` | 否 | `org`（默认，全员）/ `dept`（需 `scope_ref`=部门ID）/ `user`（需 `scope_ref`=用户ID） |
| `scope_ref` | 条件 | `dept`/`user` 时**必填** |
| `stages` | ✅ | 节点数组；`stage`（**稳定编码，创建后不要改**）、`seq`（顺序）、`name`（中文名）、`manual_minutes`（人工基线分钟，可空=未采集）、`methods`（**映射**，见下） |

**`methods` 的写法（关键）**：填 `<插件标识>.<方法名>`，与 `local_service_call` 的 `service_name.method_name` 完全一致（例：`kitchen.buy`）。**写在这里表示"这个方法属于本工作流的某个节点"**，也决定了入口强制的判定依据。填错 → 该步骤不会被拦截。

**出参**：

```json
{ "code": 200, "data": { "revived": false, "version": 1 } }
```

- `revived = true` 表示该编码此前被**逻辑删除**过，本次是**复活式重建**（版本号在原基础上 **+1**，不是从 1 开始）。**前端可据此提示"已恢复并覆盖历史定义"**。

### A3. 详情

```
GET /biz/gis_workflow/{code}
```

```json
{
  "code": 200,
  "data": {
    "workflow": {
      "biz_scene": "dish", "name": "做菜", "description": "从买菜到上桌的完整流程",
      "status": "published", "prefix": "dish", "enforce_mode": "shadow",
      "scope": "org", "scope_ref": null, "current_version": 2
    },
    "stages": [
      { "scene": "dish", "stage": "buy", "seq": 1, "name": "买菜", "manual_minutes": 25 }
    ],
    "bindings": [
      { "id": 12, "scene": "dish", "match_type": "plugin_method", "match_value": "kitchen.buy", "stage": "buy" }
    ]
  }
}
```

> ⚠️ 注意字段名差异：工作流实体里的编码字段叫 **`biz_scene`**（历史命名，等同 `code`），列表项里叫 `code`。渲染时两者都指向同一个值。

编辑页回填建议：用 `stages` 渲染节点列表，用 `bindings` 反查每个节点已绑定的 `match_value`（**一个节点可绑多个方法**）。

### A4. 修改

```
PUT /biz/gis_workflow/{code}
```

请求体与「新建」**完全一致**（含 `stages`，**整体覆盖**：节点与映射按传入内容**全量重建**）。`stages` 必须把要保留的节点都带上，否则会被删掉。

**⚠️ 重要行为：编辑即回草稿。**
编辑一条已发布 / 已停用的工作流后，它的 `status` 会自动变回 **`draft`**，**改动不生效**，必须重新「发布」才生效。
（这是刻意设计：避免智能体正在跑流程时定义被中途换掉。）
→ 前端在编辑成功后应提示：「已保存为草稿，需重新发布才生效」。

### A5. 发布

```
POST /biz/gis_workflow/{code}/publish
```

- **仅 `draft` / `disabled` 可发布**；已是 `published` 会返回 `400 仅草稿或停用状态的工作流可发布`。
- 成功行为：`status='published'`、**`current_version` +1**、写一条变更留痕、刷新服务端缓存（**立即对智能体生效**）。
- 出参 `data` 为 `null`。

### A6. 停用

```
POST /biz/gis_workflow/{code}/disable
```

- 停用后：不再对智能体暴露（`workflow_list` / 资源 / 模板都不再出现），入口强制对该工作流**停止生效**。
- 已产生的单据不受影响。

### A7. 删除

```
DELETE /biz/gis_workflow/{code}
```

- **逻辑删除**（可被同编码"复活式重建"恢复）。
- **守卫**：若该工作流 `status` 是 `published` 或 `disabled`，且**已存在单据**，会返回：
  `400 工作流【做菜】下已有 3 张单据，不能删除；如需下线请用「停用」。`
  → 前端**不要**把删除按钮当成"下线"入口，应把「停用」作为主要动作，删除仅用于"建错了"。

### A8. 导出

```
GET /biz/gis_workflow/{code}/export
```

```json
{ "code": 200, "data": { "content": "{\"code\":\"dish\",\"name\":\"做菜\",...}" } }
```

- `content` 是**字符串形式的 JSON**（要下载成 `.json` 文件就给这个字符串）。
- 导出**只含定义**（编码/名称/说明/前缀/强制模式/域/版本/节点+方法），**不含**运行数据、单据、留痕。

### A9. 导入

```
POST /biz/gis_workflow/import
```

```json
{ "content": "<A8 导出的那个字符串>", "conflict": "skip" }
```

| `conflict` | 行为 |
|---|---|
| `skip` 或省略 | 编码已存在 → 跳过，不覆盖 |
| `overwrite` | 编码已存在 → 覆盖定义 |

- 导入新建的工作流一律落 **`draft`**，需要再「发布」。
- 常见错误：`content` 不是合法工作流 JSON → `400 导入内容不是合法的工作流 JSON: ...`（前端可把原始 `msg` 直接展示）。

### A10. 变更历史

```
GET /biz/gis_workflow/{code}/changelog?page=1&page_size=10
```

```json
{
  "code": 200,
  "data": {
    "total": 2,
    "rows": [
      {
        "log_id": 3,
        "workflow_code": "dish",
        "version": 2,
        "change_type": "publish",
        "change_note": null,
        "before_snapshot": "{...JSON 字符串...}",
        "after_snapshot": "{...JSON 字符串...}",
        "operator": "admin",
        "created_time": "2026-10-14 20:39:10"
      }
    ]
  }
}
```

`change_type` 枚举与建议展示：

| 值 | 含义 |
|---|---|
| `create` | 新建（复活式重建时 `change_note` 会写明） |
| `publish` | 发布（版本 +1） |
| `disable` | 停用 |
| `update_scene` | 编辑（`change_note` = "编辑后回到草稿状态，需重新「发布」才生效"） |
| `update_stage` / `update_binding` | 节点 / 映射变更 |
| `import` | 导入 |
| `delete` | 删除 |

> `before_snapshot` / `after_snapshot` 是**该版本的完整定义快照字符串**（不是增量 diff）。需要"对比"界面时自行解析这两个 JSON。时间线展示建议按 `created_time` 倒序。

## 四、接口契约 B：单据侧（看板 / 列表 / 详情 / 作废）

> 路由前缀：`/prod-api/biz/gis_biz_object`
> 这些接口**原本就有**，本次变化：**多一个状态档 `cancelled`** + **多两个统计字段** + **多一个作废接口**。

### B1. 看板汇总

```
GET /biz/gis_biz_object/summary?begin_time=&end_time=&stall_days=7
```

```json
{
  "code": 200,
  "data": {
    "begin_time": null, "end_time": null, "stall_days": 7,
    "total_docs": 12,
    "stalled_total": 2,
    "cancelled_total": 1,
    "unassigned_calls": 5,
    "scenes": [
      {
        "biz_scene": "dish", "scene_name": "做菜",
        "total": 8, "open_cnt": 1, "in_progress_cnt": 2, "done_cnt": 4, "failed_cnt": 0, "cancelled_cnt": 1,
        "stalled_cnt": 2,
        "avg_actual_minutes": 42.5,
        "baseline_minutes": 65,
        "compression_rate": 34.62
      }
    ]
  }
}
```

**本次新增字段**：

| 字段 | 位置 | 说明 |
|---|---|---|
| `cancelled_cnt` | 场景行 | 该场景**作废**单据数 |
| `cancelled_total` | 顶层 | 全部作废单据数 |

**两个口径要跟前端说清**：

1. `compression_rate` 是**百分数**（0~100，保留 2 位），不是小数比例。`null` = 基线未采集或基线 ≤ 0，**不要显示成 0%**，建议显示 `—`。
2. `unassigned_calls` = **未携带单号的调用次数**（无法归属到任何单据）。
   非管理员只能看到**自己发起的**未归调用，所以这个数字对不同用户是不同的；它是"链路断点"的提示指标，不是单据数。
3. `scenes` 里**不含**无归属单据（`biz_scene` 为空的单据不在场景列表里），只体现"有工作流归属"的单据。

### B2. 单据列表

```
GET /biz/gis_biz_object?biz_object_id=&biz_scene=&status=&stalled=&stall_days=7&begin_time=&end_time=&page=1&page_size=10&order_by=last_call_time&is_asc=false
```

| 参数 | 说明 |
|---|---|
| `biz_object_id` | 单据号，**模糊匹配** |
| `biz_scene` | 工作流编码；为空 = 全部（**含无归属单据**） |
| `status` | `open` / `in_progress` / `done` / `failed` / **`cancelled`** |
| `stalled` | `true`=只看停摆；`false`=只看未停摆；不传=全部 |
| `stall_days` | 停摆阈值（天），默认 7 |
| `begin_time` / `end_time` | 按**单据开始时间**过滤，支持 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM:SS` |
| `order_by` | 默认 `last_call_time`；`is_asc` 默认 `false`（倒序） |

行结构与原有一致（`biz_object_id` / `biz_scene` / `scene_name` / `title` / `status` / `current_stage` / `stage_name` / `owner_id` / `started_time` / `last_call_time` / `ended_time` / `call_count` / `stalled` / `silent_days`）。

- `stalled` 是 `0/1` 数值（不是布尔），`1` 表示"静默已超阈值且单据未结束"——**只做提示，不代表单据状态变了**。
- `scene_name` / `stage_name` 未配置时为 `null`，请回落显示编码 / 空。

### B3. 单据详情

```
GET /biz/gis_biz_object/{biz_object_id}
```

```json
{
  "code": 200,
  "data": {
    "doc": { "...同列表行结构..." },
    "plan": [ { "stage": "buy", "seq": 1, "name": "买菜", "manual_minutes": 25, "hit_count": 3 } ],
    "timeline": [
      {
        "log_id": 9001, "created_time": "2026-10-14 20:41:02", "user_name": "admin",
        "tool_name": "local_service_call", "plugin_name": "kitchen", "method_name": "buy",
        "stage": "buy", "stage_name": "买菜",
        "success": true, "result_code": null, "result_msg": null, "error_type": null,
        "elapsed_ms": 128,
        "approval_id": null, "handover": false, "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
      }
    ],
    "actual_minutes": 42.5,
    "baseline_minutes": 65,
    "compression_rate": 34.62
  }
}
```

- `plan` = 该工作流的**节点计划**（含每个节点已发生的调用次数 `hit_count`，可用于"哪一步没走"）。
- `timeline` = **端到端时间线**（每次调用一行，含被业务闸门拒绝的调用——`success=false` + `result_msg` 为拒绝原因）。
- `trace_id`：调用方传了 W3C `traceparent` 时才有值，可用于与其他系统对账。
- **不可见时返回 `404 请求的资源不存在`**（不是 403）——这是刻意的：不泄露"该单据是否存在"。

### B4. 单据作废（**新增**）

```
POST /biz/gis_biz_object/{biz_object_id}/close
{ "reason": "客户取消订单" }
```

- `reason`：**必填非空**（后端会校验；作废原因会落到留痕表，可审计）。
- 权限：**能看见该单据即可作废**（叠加工作流可见域）+ 管理员。
- 行为：`status='cancelled'` + 写入 `ended_time`。
- 失败情形：
  - 已在终态（`done` / `failed` / `cancelled`）→ `400`，文案说明已结束；
  - 原因空 → `400`；
  - 单据不可见 → `403`。

**前端交互建议**：按钮放详情页；二次确认弹窗（必填原因）；成功后刷新详情与列表/看板（`cancelled_cnt` 会变化）。

### B5. 停摆告警（沿用，无字段变化）

```
GET  /biz/gis_biz_object/stall_alert/list
POST /biz/gis_biz_object/stall_alert/scan     ← 手动触发一次巡检
```

- `scan` 由**管理员**触发；出参无业务数据，成功后刷新列表即可。
- 停摆**只做提示，绝不修改单据状态**——UI 上不要写成"已中止"。

## 五、接口契约 C：技能库的「流程技能」（**口径已改，请注意**）

**新口径：流程技能由「工作流」自动生成，不再由人手写技能声明。**

| 项 | 值 |
|---|---|
| 技能名 | **`workflow:<工作流编码>`**（例 `workflow:dish`） |
| 来源 | **系统生成**（虚拟，不落盘、不写知识库；从工作流定义 + 插件注册表实时渲染） |
| 生成条件 | 工作流**已发布**且**对当前用户可见**（与 `workflow_get` 同口径） |
| 内容 | 名称 / 说明 / 操作说明（怎么带单号）/ 步骤清单 + **每个方法的参数摘要** |

**技能库接口本次「不用改」** —— 保持原样即可（下面只说"别做什么"）：

## 七、页面约定

### 7.1 工作流管理页（管理后台 / controller）

**列表**：编码 / 名称 / 状态 / 强制模式 / 可见域 / 节点数 / 当前版本 / 操作。

**操作按钮显隐**（照抄服务端判定，别自己算）：

| 按钮 | 显示条件 |
|---|---|
| 编辑 / 删除 / 导入覆盖 | `can_manage === true` |
| 发布 | `can_manage && status !== 'published'` |
| 停用 | `can_manage && status === 'published'` |

**编辑页（核心交互：拖拽 + 下拉 —— 明确要求，别做成手填编码/ID）**

> 工作流是**核心能力**，编辑体验要"能拖、能选"，不要让人手打 `stage` 编码或部门/用户 ID。

| 区域 | 交互 | 数据源（**都已存在，无需新接口**） |
|---|---|---|
| **左：能力库** | 插件 → 方法 两级树 + 搜索 | 插件列表：`GET /biz/gis_service`（返回 `Vec<PluginManifest>`，含 `methods[].name / description / inputSchema`）<br>单个插件完整方法：`GET /biz/gis_service/{plugin}` |
| **中：工作流画布** | 把方法**拖进来**，自动成为**一个节点**；节点可**上下拖动排序**（写 `seq`） | — |
| **右：节点属性** | 名称（必填）、人工基线（可选）、该节点关联的方法 | — |
| **可见域** `scope` | 单选：全员 / **指定部门（下拉）** / **指定用户（下拉）** | 部门下拉：`GET /biz/gis_user_dept`<br>用户下拉：`GET /biz/gis_user/picker?keyword=&page=1&page_size=20`（**专为选择器设计**，支持搜索+分页） |
| **强制模式** `enforce_mode` | 单选（影子 / 强制），带一句说明 | — |

**拖拽的映射规则（前端一定要对齐）**：

1. **拖一个方法进来 = 建一个新节点**。
   - `stage`（节点编码）前端可**自动生成**：方法名转小写 + 下划线（如 `wash_vegetables`），**只在新建时可编辑**，编辑已有节点时**锁住**（它要落进调用日志、要被校验引用，改了历史单据就对不上）。
   - `name` 默认取方法 `description` 的短句（或方法名），可改。
2. **把方法拖到已有节点上 = 给该节点加一个方法**（多选）。
   - **推荐：一个节点一个方法**（粒度清晰、参数摘要好读）；一个节点绑多个只用于"这一步确实要调多个方法"。
3. **同一个方法不要拖两次进同一条工作流**（后端唯一键会拒）；同一个方法**可以**用在多条不同工作流（入口判定会按单号反查消歧，不会失效）。
4. `manual_minutes`（人工基线）可空；为空时详情/看板的压缩率会显示 `—`。
5. `scope=dept / user` 时**必须**选 `scope_ref`（下拉选出来的值）。
6. **保存后提示「已保存为草稿，需重新发布才生效」**（见 A4）。

**导入/导出**：导出给下载按钮（`.json`，文件名建议 `{code}.json`）；导入给文件选择 + `conflict` 单选（`skip` / `overwrite`）。

**变更历史**：侧栏或 Tab 展示，按 `created_time` 倒序，字段见 A10。

## 八、错误处理约定

| 场景 | HTTP/`code` | 前端处理 |
|---|---|---|
| 无权限 | `code` 对应权限不足（403 语义） | 提示"无权限"；按钮应已被 `can_manage` 隐藏 |
| 资源不存在（含单据不可见） | `404 请求的资源不存在` | 提示"不存在或无权查看"（**不要**区分"不存在"和"无权"，会泄露信息） |
| 编码已存在（新建） | `400`，msg 说明 | 提示改用其他编码；若要复用已删除编码，直接重试即可（会走复活式重建） |
| 仅草稿/停用可发布 | `400 仅草稿或停用状态的工作流可发布` | 刷新列表（状态可能已被他人改动） |
| 有单据不能删除 | `400 工作流【X】下已有 N 张单据…` | 引导改用「停用」 |

> 通用做法：**直接把后端 `msg` 展示给用户**——这些文案已写成可直接展示的中文。

## 九、已知限制 / 坑（务必知道）

1. **列表类接口一次最多返回 200 条**（服务端 clamp）：工作流列表、资源/模板列表在大规模时会截断。当前数量级无影响；超过时需要分页遍历（工作流管理页请用分页，不要拉全量）。
2. **编辑即回草稿**（A4）：这是最容易被前端漏掉的行为，务必加提示。
3. **`biz_scene` vs `code`**：工作流实体/详情里叫 `biz_scene`，列表里叫 `code`，同一个值。
4. **删除不是下线**：删除有单据守卫，下线请用「停用」。
5. **`can_manage` 是服务端判定结果**：不要用 `scope` 自己推断按钮权限（部门负责人的判定逻辑在前端拿不到数据）。
6. **状态筛选不传 ≠ 只看已发布**：工作流列表不传 `status` 会返回全部（含草稿/停用），这是管理台语义；而智能体侧（MCP）只会看到已发布的。
