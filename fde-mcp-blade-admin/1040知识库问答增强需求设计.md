# 1040 知识库问答增强需求设计

> 想法 / 需求 / 实际进度 / 待完成 / 优化 / 问题处理。本文自包含。
> 日期：2026-09-30 ｜ 编号：1040 ｜ 范围：**检索侧增强（A）+ 问答自检（B）**

## 一、先说定位：我们只做「检索」与「体检」，不做「生成」

业界把「知识库问答」做成一条 **8 层管道**，每层对下一层交契约：

| # | 层 | 交出什么 |
|---|---|---|
| 1 | 摄取/解析 | 保留结构的文本 + 文档版本 + 来源元数据（按标题层级/表格边界做结构切分） |
| 2 | 索引 | 带稳定 ID、向量、**关键词索引**、权限元数据的切块 |
| 3 | 查询理解 | 意图 + 改写后的 query（别名/缩写展开、多库路由） |
| 4 | 检索（带权限） | 该用户有权看的候选块 + 分数（权限是**过滤条件**，不是召回后再过滤） |
| 5 | 重排 | 去重、按真实相关性排序的短名单 |
| 6 | 上下文装配 | 在 token 预算内的证据包，每条带引用编号 |
| 7 | 生成 | 带引用的答案，或**诚实拒答**（低置信不硬答） |
| 8 | 评估与可观测 | 离线黄金集 + 指标 + 线上缺口日志，任何答案可归因到层 |

**本系统的定位**（工具侧中控，不承担大模型推理与 Agent 编排）决定了：

- **第 7 层「生成」不属于我们** —— 由客户自己的 Agent（Claude / Cursor / Dify / 自研）完成；
- **我们负责第 1~6 层（检索侧）**，交出可靠的「证据」；
- **以及第 8 层前半（评估侧）**，证明「证据是可靠的」。

> 一句话：**我们不做问答机器人，我们做问答机器人的"可靠后厨"，并且自带体检。**

## 二、本功能的两块范围

| 块 | 做什么 | 对应上面的层 |
|---|---|---|
| **A 检索侧增强** | 让召回的**是对的、排在前面**，并且**知道自己不确定** | 4 / 5 / 6 层 |
| **B 问答自检** | 用探针问题验证"每篇文档问得出来吗" —— **静默失效必须能被发现** | 8 层（评测） |

## 三、A 检索侧增强

### 3.1 需求

| # | 需求 | 说明 |
|---|---|---|
| **A1** | **相似度阈值 + 低置信标注** | `kb_search` 支持可配阈值（默认 0.45）：低于阈值的命中不返回；命中不可靠时**在返回文本里加一行 `[低置信] …` 提示**（MCP 工具返回的是**给模型读的文本**，不是结构化 JSON），让 Agent 自己决定要不要说"知识库没有依据" |
| **A2** | **轻量混合检索** | 纯向量对**专有名词 / 型号 / 函数名**很差。用"查询 n-gram 在标题与正文里的命中率"算一个稀疏分，与向量分加权融合。**不引入中文分词库**（本系统当前没有 jieba 之类的依赖），用 n-gram 子串统计实现 |
| **A3** | **别名 / 同义词表** | 用户问「打码」，文档写「脱敏」；问「二维码」，文档写「扫码接入」。检索前按别名表扩展 query，提升召回 |
| **A4** | **证据包增强** | `kb_search` 每条命中返回 `doc_title / source_uri / chunk_no / score`，让 Agent 能写出「依据《XX》第 N 段」的引用 |

### 3.2 口径（写死）

- **阈值语义**：`score < min_score` 的命中**直接丢弃**，不返回；`min_score` 存在 `gis_sys_config`（键 `kb.min_score`），默认 `0.45`。
- **低置信判定**：过滤后**结果为空**，或 **Top1 分数 < `kb.low_conf_score`（默认 0.55）** → `low_confidence = true`、`suggest_no_answer = true`。
- **混合分公式**：`final = (1 - w) * cosine + w * kw`，其中 `w = kb.hybrid_weight`（默认 `0.3`）；
  `kw = max(正文 n-gram 命中率, 1.5 × 标题 n-gram 命中率)`，n 取 2~4，命中率 = 命中的 n-gram 数 / 查询总 n-gram 数，上限 1.0。
- **别名扩展**：`query' = query + " " + 命中的 canonical 值`；**只用于 embedding 检索**，原始 query 照常回显。
- **排序稳定**：新公式只在**同一批候选中重排**，不扩大召回集（先向量召回 `top_k × 3`，再算混合分取 `top_k`）。

### 3.3 举例（验收时用）

| 查询 | 现在 | 期望 |
|---|---|---|
| `gis-pump-01` | 纯向量可能被"设备""泵"淹没 | 标题/正文精确命中 → 该片段排到 Top1 |
| 「打码怎么配」 | 可能零命中（文档写"脱敏"） | 别名表把「打码 → 脱敏」扩展进去 → 召回《PII 脱敏配置指南》 |
| 「公司年会在哪开」 | 返回 Top-5 全是 0.2~0.3 的噪声 | 阈值过滤后结果为空 + `suggest_no_answer=true` |

## 四、B 问答自检

### 4.1 需求

| # | 需求 | 说明 |
|---|---|---|
| **B1** | 探针问题可维护 | 每篇文档可配若干条问题（管理员手写）；**没手写时系统按文档标题自动补 1 条**，保证覆盖率 100% |
| **B2** | 一键自检 | 点「立即自检」，用该索引下全部探针检索一遍，产出结果 |
| **B3** | 自动自检 | 「同步」/「强制重建」成功后自动跑一次，无需人工点击 |
| **B4** | 判定与记录 | 每条探针记录：期望文档、实际 Top1 命中文档、期望文档排名、Top1 相似度、是否通过、耗时 |
| **B5** | 告警 | 文档级"0 条探针命中" = 不可召回 → 页面标红 + 后端日志 warn |
| **B6** | 结果可查 | 看到最近一次自检的汇总与明细，支持"只看未通过"过滤 |

### 4.2 口径（写死）

- **单条通过**：期望文档出现在 **Top-5** 内即通过；期望文档排名 `hit_rank` 从 **1** 起，**未命中记 0**。
- **文档级**：至少 1 条探针通过 → 「可召回」；0 条通过 → 「**不可召回**」（告警）。同时展示「命中率 = 通过题数 / 总题数」。
- **自动题**：`source=auto`，内容 = 文档标题原文；**手写题**：`source=manual`。
- **为什么文档级用"任一题通过"**：自动题（标题）召回率天然偏低，用"全部通过"会大量误报；自动题负责"发现整篇丢失"，手写题负责"发现答非所问"。

### 4.3 对应业界指标（说明我们做的是哪一段）

业界用 RAGAS 四指标，它们分属不同层：

| RAGAS 指标 | 测哪层 | 我们是否做 |
|---|---|---|
| Context Recall（该召回的召回了吗） | 检索层 | ✅ **B 做的事**（= 文档可召回率） |
| Context Precision（相关的排前面了吗） | 检索层 | ✅ **B 做的事**（= Top1 命中率 / 期望文档平均排名） |
| Faithfulness（答案有没有超出上下文） | 生成层 | ❌ 不做（需 LLM，属生成层） |
| Answer Relevance（答的是不是这个问题） | 生成层 | ❌ 不做（同上） |

**这是本功能最关键的取舍**：我们只看"证据给得对不对"，**不需要 LLM 裁判**，因此在 2C2G 的内网机器上也能跑。

## 五、不做清单（含原因）—— 用于拒答，有据可查

| 不做 | 为什么不做 | 想要的话怎么办 |
|---|---|---|
| 生成答案 / 拒答话术 / 引用化行文 | 本系统定位是**工具侧中控，不承担大模型推理与 Agent 编排**；且数据不出内网，生成放客户自己的 Agent 侧更合规 | 客户 Agent 侧实现 |
| 防泄漏（答案里不回原文） | 同上，属生成层 | 客户 Agent 侧实现 |
| cross-encoder 重排模型 | 本地 CPU（体验档 2C2G）上 embedding 已是瓶颈，再挂 cross-encoder 会显著拖慢检索；我们语料是几十篇量级，收益不抵成本。**已用 A2 的轻量加权替代** | **插件化接入高级知识库专项服务** |
| GraphRAG / 知识图谱 | 我们的知识库是团队自写的 Markdown 说明文，不存在需要实体关系推理的合同/制度海 | 同上 |
| 多模态 / OCR / 表格结构化 | 来源是 Markdown，没有扫描件与复杂表格 | 同上 |
| 切块级多租户 ACL | 单部署单组织，现有"索引级可见性（`index_visible`）"已覆盖 | 同上 |
| Faithfulness / Answer Relevance | 需要 LLM 判定，属生成层，且把判断留给客户的 Agent 更合适 | 同上 |
| 知识缺口自动推送（邮件 / IM 周报） | 首版先把"缺口"落在页面上；推送等有真实使用场景再做 | 复用既有消息中心 |
| 自检结果的趋势图 | 量小，先看"最近一次"；等接定时任务再看趋势 | 后续增强 |

### 5.1 出口：不做 ≠ 不能有 —— 插件化接入高级知识库专项服务

上面标"想要的话怎么办"的能力，**都不需要改本系统内核**。本系统已有的插件机制（`service_plugins/`，**拷贝文件夹即安装**、方法以 `local_service_*` 三步渐进发现暴露）天然可以承载一个「**高级知识库专项服务**」插件：

- 重排、GraphRAG、多模态、外部向量库（Milvus / ES / 向量数据库服务）等，都以**插件方法**的形式接入；
- 内置的 `kb_search` 保持「**轻量、离线、开箱可用**」，高级能力**按需挂载**；
- 客户不买高级服务时，系统依然完整可用；买了就装个插件文件夹。

**这就是我们敢把这些能力列进"不做清单"的底气。**

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| A2 权重 `w` 调不好 → 召回反而变差 | 检索质量下降 | 权重可配（`gis_sys_config`），默认 0.3；先按 §3.3 的对照用例回归，再放量 |
| A1 阈值定太高 → 正常问题也被拒 | 用户体验断崖 | 默认 0.45 偏保守；`low_confidence` 只是**标注**（不删结果），真正的"拒答"由 Agent 决定 |
| A3 别名表被滥用（一个词映射出十个） | query 被稀释 | 一对多限制（单别名 ≤ 5 条 canonical），并在页面显示"扩展后的 query"便于排查 |
| B 自动题（标题）召回率低 → 大量"不可召回"误报 | 告警噪音 | 文档级用"任一题通过即算可召回"；自动题失败但手写题通过时不告警 |
| B 自检跑 embedding 抢 CPU | 拖慢检索主链路 | 自检**串行**、同一时刻只允许一个 run；进行中再次触发直接拒绝 |
| 切块算法/模型变更后 B 全量告警 | 一次性大量红 | 这是**预期信号**：页面在告警卡片直接给「去强制重建」入口 |

## 九、验收标准

1. **A1**：问一个知识库里根本没有的问题 → 返回空 + `suggest_no_answer=true`；问一个存在的 → 正常返回。
2. **A2**：用含专有名词的查询（如插件方法名 `feishu.im.send_card`）→ 对应片段进入 Top1。
3. **A3**：加一条「打码 → 脱敏」别名后，问「打码怎么配」能召回《PII 脱敏配置指南》。
4. **A4**：`kb_search` 每条命中都带 `doc_title / source_uri / chunk_no / score`。
5. **B**：能对任一文档加探针；「立即自检」≤30 秒出结果；
   人为把一篇文档挪到不被扫描的目录 → **该文档被标为「不可召回」**；挪回后告警消失。
6. **B**：「同步」/「强制重建」成功后**自动**产出一轮自检结果。
7. 全部改动**不新增菜单**（挂在既有「管理中心 › 平台能力 › 向量知识库」页内），权限沿用该页现有权限点。
